# Encrypted hosting application inventory

This manually dispatched workflow prepares a read-only inventory of the already configured MochaHost/cPanel account. It cannot deploy, restart, change DNS, run migrations or activate providers. `collect_inventory` defaults to `false`; collection is allowed only on `main`, through the `production` environment. That label does not establish reviewer protection; actual environment protection depends on the repository settings.

The only UAPI operations are `/usr/local/cpanel/bin/uapi --output=json PassengerApps list_applications` and `/usr/local/cpanel/bin/uapi --output=json DomainInfo single_domain_data domain=takatak.ca`, run as the existing SSH account without sudo or a `--user` override. The [cPanel CLI documentation](https://api.docs.cpanel.net/cpanel/introduction) requires that full binary path on CloudLinux. [PassengerApps list_applications](https://api.docs.cpanel.net/specifications/cpanel.openapi/application-manager/passengerapps-list_applications) is documented as read-only and applies to applications already registered in Application Manager; newer Web Apps and a separate CloudLinux Node selector can have a different inventory. This workflow does not query those alternatives or scan directories when PassengerApps is unavailable.

A small reviewed Python script is sent over SSH stdin, without writing a host file. It discards environment **values**, dependency commands, unrelated domains and API messages on the host before SSH stdout. Only `takatak.ca` / `ahmverdun.ca` app name, root, explicitly returned startup filename, environment variable names and bounded enabled/disabled/unknown status survive. The current PassengerApps schema does not provide a startup filename, so its `startupFile` is normally null. It is never inferred as `server.js`.

[DomainInfo.single_domain_data](https://api.docs.cpanel.net/specifications/cpanel.openapi/domain-information/domaininfo-single_domain_data) is restricted to `takatak.ca`; only its domain and document root survive. A document root is not proof of a Passenger application root. Missing Python/API support, malformed responses and transport failure produce bounded unavailable status without any raw error details.

If that canonical document root is inside the current SSH account's home (identified by current UID), the script reads only its existing `.htaccess`, at most 64 KiB. It rejects configuration symlinks and projects only `PassengerAppRoot`, `PassengerStartupFile`, `PassengerNodejs`, `PassengerAppType` and `PassengerEnabled`. `SetEnv` and every other line are discarded on the host. [cPanel's Node.js documentation](https://docs.cpanel.net/knowledge-base/web-services/how-to-install-a-node.js-application/) describes the Passenger root/startup/type directives; some hosts keep them in Apache includes instead of `.htaccess`. Includes elsewhere are not inspected by this workflow. Conflicting directives or roots outside the current user's home stay unavailable.

For a selected application root confined to that home, `appRootIsSymlink` reports whether the original configured `PassengerAppRoot` itself is a symlink. `currentIsSymlink` separately checks its `current` child. For example, a configured `/home/user/app/current` pointing into a home-confined release reports `appRootIsSymlink=true`, without accidentally checking the resolved release root instead. Other optional flags report whether the explicitly named startup file and `.env` exist. Those are stat checks only: startup and environment file contents are never read. There is no recursive scan.

The runner repeats the field/domain allowlist, then encrypts the projected JSON with a fresh AES-256-GCM key and nonce. That key is wrapped using RSA-OAEP with SHA-256. The committed **public recipient key** is pinned to SPKI SHA-256 `ebcb695f859f2760aa6748e27094c12fff11cc0b114e294d1650dc89e795f785`; neither workflow input nor environment settings can substitute a recipient. The corresponding owner private key stays outside Git and is never read by this workflow.

Only `hosting-app-inventory.enc.json` is uploaded, retained for three days. Logs contain bounded status and selected-app counts; neither paths nor environment names/values are logged. Raw responses are not written on the server or runner. Temporary SSH material is removed by an always-run cleanup step. Existing host-key pins remain mandatory (`StrictHostKeyChecking yes`), and collection has a 90-second SSH bound within a five-minute job.

Envelope fields: `version`, `purpose`, `algorithm`, `recipientSpkiSha256`, `wrappedKey`, `iv`, `tag`, `ciphertext`. Binary fields use Base64. AES authenticated data is the UTF-8 JSON encoding of the first four fields in that order. Owner decryption uses RSA OAEP SHA-256 for `wrappedKey`, then AES-256-GCM with that key, `iv`, `tag` and authenticated data. Decrypted metadata must remain local to the owner's controlled workspace.

Tests use synthetic API/file fixtures and an in-memory fixture RSA key. They verify discarded secret fields, unrelated-domain rejection, unavailable schemas, the single confined configuration read, stat-only flags, symlink/outside-home rejection, encryption/decryption, authentication of ciphertext/metadata, the real public-key pin, static UAPI commands and the manual/main-only workflow contract. No test connects to hosting or reads the owner's private key.
